# Mock Interview Transcript（示例）

说明：这是一个“项目深挖 + 追问 + 纠偏”的演示稿，展示 Skill 如何把用户从危险表达拉到可过甚至强回答。

## 背景

岗位：大模型应用开发实习生  
项目：内部文档 RAG + Agent demo  
风险：用户习惯写“提升准确率”，但无统计口径

## Round 1：真实性与边界

面试官：
你这个项目上线了吗？

候选人（初始回答，危险）：
算是上线了吧，团队有人在用。

面试官追问：
“算是”具体是什么意思？有没有真实用户、监控和 SLA？

候选人（纠偏后）：
项目是内部 demo，有小范围试用，但没有正式线上发布和 SLA。我在简历里不会写“线上落地”，只写“内部试用和流程验证”。

点评：
- 危险点：把内部试用混同为上线。
- 修正点：明确边界，避免过度 claim。

## Round 2：贡献边界

面试官：
你说做了 Agent，具体你做了哪些，哪些不是你做的？

候选人（初始回答，偏空）：
主要是做了优化和一些联调。

面试官追问：
优化什么？输入输出是什么？同事负责什么？

候选人（可过）：
我负责三块：问答样例整理、Prompt 模板维护、文档切分和向量入库链路联调。  
底层模型选择和部署不是我做的，由同事负责。  
我的输出是 bad case 分类、链路问题清单和可复用的校验规则建议。

点评：
- 危险点：使用“优化”“联调”但没有对象和边界。
- 修正点：按模块拆分职责，主动讲“我做/我没做”。

## Round 3：指标与证据

面试官：
简历写了“提升准确率”，口径是什么？

候选人（初始回答，危险）：
我们看起来提升挺明显的。

面试官追问：
“看起来”不是指标。你有评估集吗？

候选人（强）：
这个项目在我参与阶段没有完整线上统计口径，所以我不应该直接写“准确率提升”。  
我后来补了固定样例集，把评估拆成 `citation accuracy` 和 `answer relevance` 两个维度，版本比较时只用同一批样例和同一标注标准。  
当前我会把简历改成“基于样例集完成回归分析和 bad case 收敛”，不写夸张数值。

点评：
- 危险点：主观感受替代指标。
- 修正点：先承认证据不足，再给可复验口径。

## Round 4：工程化深挖

面试官：
如果模型输出 JSON 缺字段，你怎么处理？

候选人（可过）：
我会在后处理增加 schema 校验。缺字段时先触发一次重试，再走人工复核队列，避免错误结果直接进入下游。

面试官追问：
怎么定位是模型问题还是上游输入问题？

候选人（强）：
链路里加 `trace_id` 和节点日志，记录输入摘要、模板版本、调用耗时和错误类型。  
先看错误是否集中在特定输入类别，再看是否与模板版本变更相关。这样能区分“输入脏数据”与“模型输出不稳”。

点评：
- 可过到强的关键：从“处理动作”上升到“定位框架”。

## Round 5：总结评分（示例）

```text
当前评级：中上（可投递，仍有风险）
加分项：
1) 能清晰讲个人边界
2) 愿意降级不实 claim
3) 有 bad case 与工程化意识

主要风险：
1) 指标体系刚建立，证据深度不足
2) 没有正式上线数据，需控制结果表达
3) 系统级稳定性案例不够丰富
```

## 可直接复用的话术

```text
这个项目是内部试用阶段，不是正式生产系统，我不会写成线上落地。
我负责的是应用工程化环节：样例、Prompt、链路联调、bad case 和校验策略。
对“效果提升”这类表达，我只在有固定评估口径后再写具体结果。
```
