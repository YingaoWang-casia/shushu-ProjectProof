# Project Diagnosis Rubric

用于判断项目是否像 toy、是否能打大厂项目面、离 SP/SSP 还有多远。

## Toy 感来源

| 维度 | Toy 表现 | 补强方向 |
| --- | --- | --- |
| 业务场景 | 只说实现功能，没有用户/流程 | 补真实用户、业务动作、前后流程 |
| 个人贡献 | 只写参与开发 | 写清模块、接口、规则、实验、文档 |
| 输入输出 | 不知道数据从哪来到哪去 | 写输入字段、输出格式、消费者 |
| 工程闭环 | 没有异常、日志、测试、部署 | 补校验、日志、测试、README、部署 |
| Bad case | 没有失败案例 | 整理失败样例、定位、修复、兜底 |
| 指标证据 | 只有“提升效率” | 补抽样、对账、耗时、准确率、覆盖率 |
| 上线状态 | 模糊说上线/落地 | 讲清生产、试用、demo、本地 |
| 技术取舍 | 只堆技术名词 | 说明为什么选、为什么不用、代价 |
| 复杂度 | 数据/流量/用户都不清楚 | 写真实规模和扩展方案 |

## 大厂强面评价信号

- 能说清业务问题和目标，而不是只背技术栈。
- 能讲清主链路：入口、处理、状态、输出、异常。
- 能承认边界，不把没做过的东西硬说成主责。
- 有 bad case 和复盘，而不是只有成功路径。
- 有工程化动作：测试、日志、监控、部署、权限、回滚、评估。
- 有 trade-off：成本、性能、准确率、用户体验、开发周期、维护成本。
- 有可迁移能力：从小公司项目抽象出大厂也认可的工程能力。

## SP/SSP 差距诊断

| 档位 | 项目表现 |
| --- | --- |
| 普通可投 | 能讲清做了什么，有基本技术栈和项目产出 |
| 强可投 | 有真实业务、有个人贡献、有 bad case、有工程闭环 |
| SP 候选 | 有 ownership、复杂取舍、指标/证据、能系统性复盘 |
| SSP 候选 | 有明显超出实习生的主动性：定义问题、推动方案、影响他人或流程，并能顶住高压深挖 |

## 输出格式

诊断时先给：

1. 当前项目竞争力档位。
2. 最危险的 5 个漏洞。
3. 最值得补的 3 个证据。
4. 最能冲高评级的 1-2 个增强点。
