# Role: Agent 开发 / 工具调用 / 工作流自动化

适用：LLM Agent、自动化工作流、客服 Agent、运营 Agent、代码 Agent、工具调用、Function Calling、多轮任务编排。

## 大厂看重点

- Agent 不等于聊天机器人。要说明它能感知状态、选择工具、执行动作、校验结果、失败兜底。
- 能讲清任务编排：planner、tool caller、memory/session、executor、verifier、human review。
- 能处理工具调用失败、参数错误、多轮状态混乱、权限、成本和不可控输出。
- 如果 Agent 面向文档问答/知识库，要补文档 RAG 生产细节：表格、跨页、引用、权限和评估。读取 `document-rag-production-gaps.md`。

## Toy 感

- 只有一个 prompt + API，没有工具调用。
- 工具调用没有 schema、权限、超时、重试、fallback。
- 没有状态管理，用户多轮对话会串。
- 没有 bad case 集，调 prompt 靠感觉。
- 没有人工复核，错误输出直接进入业务。
- 文档 Agent 只做问答，没有考虑文档解析、表格召回、引用页码、权限过滤和索引更新。

## 可补强动作

半天：

- 列出 Agent 能调用的工具、每个工具输入输出和失败类型。
- 整理 10 条失败样例：幻觉、参数错、工具超时、格式错、状态串线。
- 写出“用户输入 -> 意图识别 -> 工具选择 -> 执行 -> 校验 -> 回复/复核”链路。

1 天：

- 给工具调用加 JSON Schema 或参数校验。
- 增加 trace_id 日志，记录 user query、tool name、params、result、error。
- 增加失败重试和 fallback 提示。

3 天：

- 做 prompt/version + bad case 回归表。
- 加人工复核状态：待确认、已通过、已驳回、需重试。
- 增加 session/memory 边界：只保留必要上下文，避免跨用户污染。
- 如果是文档 Agent，补 query-answer-evidence 评估集，覆盖表格、跨页、无答案拒答和权限问题。

1 周：

- 做 Agent 任务看板：调用记录、失败原因、复核状态、成本统计。
- 增加权限控制：不同用户可调用不同工具。
- 增加评估集：任务成功率、工具调用准确率、人工复核通过率、平均延迟。

## 简历表达素材

保守版：

```text
参与内部业务 Agent 原型开发，负责 Prompt 模板维护、工具调用样例整理和历史数据清洗；梳理模型输出不稳定、字段缺失和工具调用失败等 bad case，为后续工程化改造提供依据。
```

标准版：

```text
参与内部业务 Agent 工具开发，负责工具调用参数校验、结构化输出约束和 trace 日志记录；针对模型幻觉、字段缺失、工具超时和多轮状态混乱等问题补充 bad case 回归、失败重试和人工复核流程。
```

偏强版：

```text
负责将内部业务 Agent 从一次性 demo 改造为可追踪、可复核的任务流程，设计工具调用 schema、异常重试、trace_id 日志和人工审核状态流；沉淀 bad case 集和回归测试样例，提升问题定位和迭代效率。
```

## 高频追问

1. 你的 Agent 和普通 chatbot 区别是什么？
2. Agent 能调用哪些工具？工具输入输出是什么？
3. 工具调用失败怎么办？
4. 模型输出参数错怎么办？
5. 多轮对话状态怎么保存？怎么避免串用户？
6. 有没有 human-in-the-loop？
7. 怎么评估 Agent 成功率？
8. 成本和延迟怎么控制？
9. 权限怎么做？模型能不能调用危险工具？
10. 如果重新设计，你会怎么做 planner/verifier？
11. 如果 Agent 基于文档回答，怎么保证引用真的支持答案？
12. 文档里的表格、跨页内容、目录和页眉页脚怎么处理？

## 回答防线

- 不说“自主智能体很强”，要说“在限定业务场景内，通过工具调用和校验完成半自动流程”。
- 不说“完全替代人工”，要说“生成草稿/建议，关键节点人工复核”。
- 不说“优化模型”，要说“优化调用链路、输出约束和失败处理”。
