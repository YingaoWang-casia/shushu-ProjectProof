
可过回答：

```text
我主要做的是应用工程侧：RAG、Prompt、评测和部分微调试验，没有做底座预训练。
```

强回答：

```text
我的核心边界是 LLM 应用算法工程，不是底座预训练。具体负责检索链路、评测集、bad case 回归和小规模 LoRA 试验。涉及模型训练能力我会明确标注为“补做后可写”，不夸大成预训练或完整对齐流程。
```

## Q2：Self-Attention 为什么要除 `sqrt(d_k)`？

危险回答：

```text
这是论文里的公式，效果更好。
```

可过回答：

```text
为了避免点积值过大导致 softmax 过于尖锐，梯度变差。
```

强回答：

```text
当维度增大时，QK 点积的方差会增大，不缩放会让 softmax 进入饱和区，训练不稳定。除以 `sqrt(d_k)` 相当于控制数值尺度，让注意力分布和梯度更可训练。
```

## Q3：为什么 decoder-only 常用于生成式模型？

危险回答：

```text
因为 GPT 都这么做。
```

可过回答：

```text
decoder-only 用自回归目标预测下一个 token，和生成任务天然一致。
```

强回答：

```text
生成任务的核心是 next-token prediction，decoder-only 的 causal mask 与训练目标一致，训练和推理路径统一；同时在大规模数据和算力下扩展性好，生态和优化工具链也更成熟。
```

## Q4：RAG 和微调怎么取舍？

危险回答：

```text
微调肯定比 RAG 更好。
```

可过回答：

```text
知识更新和可追溯问答优先 RAG，风格和任务模式优化可用微调。
```

强回答：

```text
如果目标是外部知识注入、可解释引用和动态更新，优先 RAG；如果目标是输出风格、格式一致性或任务行为约束，优先 SFT/LoRA。真实业务常见组合是 RAG + 微调 + 评测闭环，用指标比较收益和成本，而不是二选一。
```

## Q5：LoRA rank 怎么选？

危险回答：

```text
我一般随便设一个值。
```

可过回答：

```text
rank 越大表达能力越强，但显存和过拟合风险也会上升，需要在验证集上调参。
```

强回答：

```text
我会把 rank 当成容量超参数：先从低 rank 起步，固定评测集观察收益曲线与延迟/显存成本，再按任务复杂度和数据规模逐步增加。若收益趋于饱和或线上稳定性变差，优先回退并补数据质量而不是盲目加 rank。
```

## Q6：SFT、RLHF、DPO 的区别？

危险回答：

```text
都是让模型更好用的方法。
```

可过回答：

```text
SFT 用监督数据学习基础指令遵循；RLHF 用偏好数据和奖励优化；DPO 直接优化偏好对，不显式训练奖励模型。
```

强回答：

```text
SFT 解决“会不会按指令做”；RLHF/DPO 解决“同样可行时偏好哪种回答”。RLHF 依赖 reward model 和 PPO，工程链路复杂；DPO 实现更简化但仍依赖偏好数据质量。实践里关键不是背定义，而是处理偏好噪声、过度拒答和安全边界误伤。
```

## Q7：如何评估一次微调是否正收益？

危险回答：

```text
看起来回答更好了就是正收益。
```

可过回答：

```text
要在固定评测集上看任务指标，并对比延迟和成本，不能只看主观体验。
```

强回答：

```text
我会固定评测集和标注口径，至少比较任务成功率/答案正确性/引用准确性/拒答准确率，并同步看 TTFT、TPOT、成本和安全指标。若离线提升但线上投诉增加，优先做分层分析和灰度回滚，不把单点离线结果当结论。
```

## Q8：为什么首 token 慢？怎么优化？

危险回答：

```text
模型大所以慢。
```

可过回答：

```text
首 token 需要完整前向和上下文计算，可通过缓存、批处理和并行优化降低延迟。
```

强回答：

```text
首 token 慢主要来自 prefill 阶段计算和调度开销。优化方向包括：缩短无效上下文、改进批处理策略、KV cache 复用、量化与并行、框架优化（如 paged attention 思路）以及请求分级。优化时要同时监控 TTFT、TPOT、吞吐、显存和质量退化。
```

## Q9：如何防 prompt injection？

危险回答：

```text
在 prompt 里写“忽略恶意输入”就行。
```

可过回答：

```text
要做工具权限隔离、输入校验和高风险操作人工确认。
```

强回答：

```text
防注入是系统问题，不是单条 prompt 问题。需要分层防护：输入清洗、上下文隔离、工具白名单与参数校验、最小权限、关键操作 human-in-the-loop、全链路审计日志。评测上要有专门注入样例并持续回归。
```

## Q10：你项目最大的 bad case 是什么，怎么解决？

危险回答：

```text
没遇到什么大问题。
```

可过回答：

```text
遇到过召回不到证据导致幻觉，后续通过混合检索和拒答策略改善。
```

强回答：

```text
典型 bad case 是“召回命中但引用错位”，导致答案看似合理但证据不支撑。排查后把问题拆成切分、重排和生成约束三层，补了 query-answer-evidence 评测集、引用校验和低置信拒答，同时记录延迟与成本变化，确保修复不是以系统稳定性为代价。
```
